# Phase 2 Task 0: flood-comparison baseline -- raw data

Coordination artifact (not committed; see task0-report.md for the reply and
gosim/flood.go for the implementation). Generated by a one-off sweep script,
not checked in; reproduction command is at the bottom of this file.

## Method

- Same sweep grid as the honest baseline: nodes {10, 50, 100}, grid topology,
  120-unit spacing (each node hears ~4 neighbors), SF10/125 kHz (sim
  defaults), 2 msg/min, 20 scripted messages over 600s, 3 seeds per point
  (1, 2, 3). Scenarios generated via `simulator/scenarios/generate.py
  --legacy N --seed S --routing {reactive,flood} [--flood-hop-limit H]`, so
  the reactive rows are byte-for-byte the same scenarios the July 2026
  honest baseline used, and the flood rows differ ONLY in the "routing"
  field.
- Every FLOOD row's 3 seeds converge to identical aggregates (same
  small-random-effect convergence the honest baseline document noted for
  the dense 10-node grid, here holding at every node count for flood too),
  so those rows are effectively one observation, not three. REACTIVE does
  NOT converge at 50/100 nodes (seed-level loose rates: 50 nodes 10%/5%/15%,
  100 nodes 0%/0%/5%; 10 nodes does converge, all three seeds at 50%/40%) --
  reactive's rate columns at 50/100 nodes are the 3-seed mean, and its
  latency columns are weighted by each seed's actual delivered-message
  count (see the table's own footnote below).
- Reactive = Bramble's real firmware AODV path (bridge_handle_receive_packet
  / bridge_handle_generate_message, unmodified by this task).
- Flood-hl3 / Flood-hl7 = Phase 2 Task 0's new managed-flooding sim-layer
  mode (simulator/gosim/flood.go), hop_limit 3 (Meshtastic's shipped
  default) and 7 (Meshtastic's max), respectively.
- Both bars, both transports:
  - LOOSE = destination ever received the DATA (broadcast-reach; how
    Meshtastic is actually used; no confirmation).
  - STRICT = the original sender received a confirmation back (reactive:
    the delivery receipt reached the sender, detected by scanning the JSON
    event stream for the `"hops"`-bearing `message_delivered` event that
    _handle_delivery_receipt emits only when it reaches the true originator
    -- NOT the same as this sim's existing `final_metrics.message_delivery_rate`
    field, see the IMPORTANT CAVEAT below; flood: a Meshtastic-style flooded
    ACK, itself hop-limited/deduped/fire-and-forget like the DATA it acks,
    reached the original sender).
- "Total tx" = final_metrics.total_packets (every successful transmission of
  every type, all nodes, summed). "Airtime by type" = ToA-weighted, read
  from `final_metrics.airtime_ms_by_type` (already ms) and reported in the
  table below in SECONDS/600s (same convention as the honest baseline doc),
  from the shared `metrics_state_t.airtime_us_by_type` accumulator both
  transports feed through the same `sim_radio_broadcast` chokepoint
  (flood's DATA lands in the `data` bucket, its ACK in the `ack` bucket,
  both via real PKT_TYPE_DATA/PKT_TYPE_ACK, not a parallel counter).

## IMPORTANT CAVEAT surfaced by this task (reactive's own metric)

This sim's existing `final_metrics.message_delivery_rate` -- the field every
prior Phase 0/1/2 document calls "delivery-with-confirmation" and uses as
THE headline number -- is measured at **destination receipt**
(`bridge.c`'s `_handle_data`, comment: "Record delivery immediately (don't
wait for receipt to arrive at source)"). It is numerically identical to the
LOOSE bar computed for this report, confirmed empirically below (reactive's
`loose_rate` equals `final_metrics.message_delivery_rate` at every point in
this sweep). It is **not** gated on the delivery receipt reaching the
sender. The STRICT bar in this report is a new, stricter measurement built
for Task 0's honest-comparison discipline (scanning for the receipt
actually reaching the originator), and it diverges from the existing metric:

| Nodes | message_delivery_rate (existing, = LOOSE here) | STRICT (receipt reached sender, this task) |
|---|---|---|
| 10  | 50% | 40% |
| 50  | ~10% (5-15% across seeds) | **0%** |
| 100 | ~1.7% (0-5% across seeds) | **0%** |

At 50 and 100 nodes, **zero** of the messages that reached their
destination ever had their confirmation make it back to the sender in this
honest sim, even though the existing metric reports ~10%/~2% "delivered."
This is a pre-existing property of the current codebase (Task 0 changed
nothing on the reactive path), not a new bug introduced here, but it means
every prior baseline document's "delivery-with-confirmation" claim at 50/100
nodes should be read as "destination reach," not "confirmed delivery" --
worth a correction pass on `docs/results/simulation-2026-07-honest-baseline.md`
if the owner wants that lineage fixed (out of scope for Task 0 to fix
itself; recorded here for the controller to act on).

## Observations

1. **Flood wins at every node count tested, on both bars, whenever its hop
   limit can topologically reach the destination.** At 10 nodes flood is
   already far ahead (100%/100% vs reactive's 50%/40%). At 50 and 100 nodes,
   with hop_limit=7 (comparable to Bramble's own `ROUTE_HOP_LIMIT_MAX=8`),
   flood is dramatically ahead: 60%/30% vs 10%/0% at 50 nodes, 90%/90% vs
   1.7%/0% at 100 nodes. This is the central-thesis-questioning result the
   framework called out as the most important possible finding: naive
   managed flooding beats Bramble's reactive AODV routing at every node
   count measured in this honest simulator, under identical modeled radio
   physics.
2. **Why: reactive's control plane is airtime-bankrupt at scale; flood's
   is not.** At 50 nodes reactive burns 682 SECONDS of RREQ ToA against a
   600s window (offered load 1.71 erlangs total, RREQ alone over 1.0
   erlang) before a single byte of the actual message payload gets a fair
   shot at the channel; at 100 nodes it's 697s of RREQ plus 645s of beacons
   against the same 600s window (2.33 erlangs offered). Flood
   (hl=7) tops out at 0.59 and 1.03 erlangs respectively at the same node
   counts -- still oversubscribed at 100 nodes (>1.0 erlang), but by a much
   smaller margin, and with ZERO discovery cost: every erlang flood spends
   is on the message itself (DATA relays) or its ACK, never on finding a
   route. Reactive re-floods RREQ from scratch for every cold discovery
   (no route cached yet at this traffic rate/topology), so its control cost
   scales with attempted messages, not just node count; flood's relay cost
   scales with node count (more potential relayers) but is bounded per
   message by hop_limit and cut further by duplicate suppression (25-27%
   of scheduled relays cancelled in the hl=7 runs).
3. **hop_limit is the dominant lever for flood, more than node count.**
   hop_limit=3 (Meshtastic's shipped default) cannot even connect most
   scripted src/dest pairs at this topology's diameter once it exceeds
   4 hops (0% reach at both 50 and 100 nodes -- this is a topology-diameter
   ceiling, not an algorithm failure: the same 10-node grid, which never
   needs more than ~3 hops, gets 100%/100% at hl=3 too). hop_limit=7
   recovers most delivery. This is a fair-comparison-basis finding, not
   just a parameter note: comparing Bramble against Meshtastic's shipped
   default at this grid size would show flood LOSING on connectivity, for
   a reason that has nothing to do with routing strategy (it is a hop-count
   budget mismatch against Bramble's own 8-hop ceiling); hop_limit=7 is the
   apples-to-apples setting against Bramble's `ROUTE_HOP_LIMIT_MAX`.
4. **10-node reactive's own STRICT bar (40%) is already below its LOOSE bar
   (50%)**, independent of flood entirely: 2 of the 10 destination-reached
   messages never had their delivery receipt make it back to the sender.
   At 50/100 nodes STRICT is 0% for reactive even though LOOSE is 10%/1.7%:
   every single confirmed-return in this sweep failed once the network was
   under load. See the IMPORTANT CAVEAT section above.

## Reproduction

Scenarios generated with (from `simulator/scenarios/`):
```
python3 generate.py --legacy {10,50,100} --seed {1,2,3} --routing reactive --out ...
python3 generate.py --legacy {10,50,100} --seed {1,2,3} --routing flood --flood-hop-limit {3,7} --out ...
```
Run each with `./bramble-gosim --headless --scenario <file>`, read
`final_metrics` / `flood_final_metrics` JSON lines, and (for reactive's
STRICT bar) scan for `message_delivered` events carrying a `"hops"` field.
The one-off aggregation script used to produce the tables above was not
checked in (ad hoc, not a maintained tool); the queries above are enough to
reproduce every number in this document.
