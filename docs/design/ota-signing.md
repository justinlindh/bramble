# OTA Firmware Signature Verification

**Status:** Implemented (software enforcement; hardware Secure Boot pending)
**Last verified:** 2026-06-12
**Audit ref:** S15 / ledger SEC-C3, NEW-SEC-2

## 1. What is enforced

Every Bramble firmware image carries an RSA-3072 signature in the ESP-IDF
Secure Boot V2 format, appended to `bramble.bin` at build time. Devices verify
that signature on every OTA write and fail closed. Three controls stack on the
OTA path:

1. **Image signature** (this document). Unsigned or wrongly-signed images are
   rejected by `esp_https_ota_finish` / `esp_ota_end` before the boot
   partition is switched. There is no transport where this is bypassed; the
   dev-only HTTP path verifies too.
2. **Origin allowlist** (`components/ota/ota_url.c`, `ota_origin.c`). The
   device downloads only from its configured OTA origin (default
   `https://bramblemesh.org/ota/`, NVS override settable solely through the
   authenticated `bramble.otaSetOrigin` RPC). `bramble.otaUpdate` takes a
   relative artifact path; raw URLs are rejected at the RPC boundary. Path
   validation is a strict charset allowlist with no traversal, no scheme
   smuggling, no percent-encoding (host-tested in `test/test_ota_url.c`).
3. **Soft anti-rollback** (`components/ota/ota_rollback.c`). An NVS-stored
   version floor rises automatically when a higher version boots and rejects
   OTA images whose `esp_app_desc` version compares lower (full semver
   precedence, host-tested in `test/test_ota_version.c`). A deliberate
   downgrade requires the authenticated `allow_downgrade` flag on
   `bramble.otaUpdate`, which also lowers the floor so the device is not
   stranded after the downgrade.

## 2. Mechanism: IDF-native signed apps, no eFuses

The implementation is ESP-IDF's signed-apps-without-secure-boot mode, not a
custom scheme. From `sdkconfig.defaults`:

```text
CONFIG_SECURE_SIGNED_APPS_NO_SECURE_BOOT=y
CONFIG_SECURE_SIGNED_APPS_RSA_SCHEME=y
CONFIG_SECURE_SIGNED_ON_UPDATE_NO_SECURE_BOOT=y
CONFIG_SECURE_BOOT_BUILD_SIGNED_BINARIES=y
CONFIG_SECURE_BOOT_SIGNING_KEY="keys/ota_signing_key.pem"
```

Why this over the earlier draft's custom Ed25519 trailer:

- **No hand-rolled crypto.** Signature generation, the image format, and the
  verification path are Espressif-maintained code already in the tree.
- **Same format as hardware Secure Boot V2.** When the human-gated eFuse step
  lands (Secure Boot V2 on a bench-validated board), the images, keys, and CI
  pipeline carry over unchanged; only boot-time enforcement is added.
- **Verification is wired into the OTA APIs we already call.** With
  `SECURE_SIGNED_ON_UPDATE_NO_SECURE_BOOT`, `esp_ota_end` and
  `esp_https_ota_finish` run `esp_image_verify` including the signature
  block. No bespoke hook points.

**Trust anchor.** Without eFuses there is no hardware root of trust, so the
trust anchor is the public key embedded in the *running* app's own signature
block: an incoming OTA image must be signed by a key that also signed the
currently running firmware. Consequences:

- A fleet running CI-built firmware accepts only release-key-signed updates.
- Every build must be signed, dev builds included; an unsigned running app
  cannot verify anything and OTA fails closed.
- Moving a device between trust domains (local dev key <-> release key)
  requires a USB flash. This is deliberate: the dev key never becomes a
  fleet trust anchor.
- The first signed release reaches existing (unsigned) fleet devices through
  a normal OTA, because the old firmware does not verify; enforcement begins
  once the signed image is running. Standard staged rollout.

## 3. Key infrastructure

| Key | Where | Used by |
| --- | --- | --- |
| Release signing key (private) | Gitea repo secret `OTA_SIGNING_KEY`; offline master copy outside the repo | CI signs every build (dev and stable channels) |
| Release public key | Committed: `keys/ota-release-pub.pem` | CI verifies built artifacts (`espsecure.py verify_signature`) |
| Dev signing key (private) | Developer machine; `BRAMBLE_OTA_SIGNING_KEY` env var, or a throwaway generated by `scripts/ensure-ota-signing-key.sh` | Local `scripts/flash.sh` builds |

The build reads the private key from the gitignored path
`keys/ota_signing_key.pem`. `scripts/ensure-ota-signing-key.sh` populates it:
from `$BRAMBLE_OTA_SIGNING_KEY` if set, else (outside CI) by generating a
throwaway dev key with a loud warning. In CI the workflow writes the secret
before the build and a missing secret fails the build; release artifacts are
never silently dev-signed.

**Dev builds policy.** Local builds sign with a dev key, so the edit-build-OTA
loop on a bench device keeps working (point the device's origin at a LAN
server via `bramble.otaSetOrigin`; `http://` origins are accepted only when
`CONFIG_BRAMBLE_OTA_ALLOW_HTTP` is compiled in). Release-channel devices
reject dev-signed images outright. The alternative (release images also
carrying a dev-key signature) was rejected because it promotes the dev key to
a fleet-wide trust anchor.

## 4. Key rotation

In the current eFuse-less mode, the release key CANNOT be rotated over OTA.
IDF verifies exactly one signature block in this mode: under
`CONFIG_SECURE_SIGNED_ON_UPDATE_NO_SECURE_BOOT`,
`esp_secure_boot_verify_sbv2_signature_block` reads only block 0 of both the
running app (the trust anchor) and the candidate image
(`secure_boot_signatures_app.c`, `secure_boot_num_blocks = 1`), and the IDF
documentation states that multiple trusted keys require full Secure Boot.
Appending a second signature block does nothing; a release signed with a new
key in block 0 is rejected by every deployed device.

What that means operationally:

- **Routine rotation**: not available over OTA. Rotating the release key
  means USB-reflashing every device with an image signed by the new key, or
  doing the rotation as part of the hardware Secure Boot migration (whose
  eFuse key-digest slots support revocation and multiple keys).
- **Key compromise**: treat the fleet as USB-recovery-only. Generate a new
  keypair offline, switch the `OTA_SIGNING_KEY` secret and
  `keys/ota-release-pub.pem`, take the OTA origin offline so the attacker
  cannot push signed-with-stolen-key images, and physically reflash each
  device. Devices the attacker already reflashed need physical recovery in
  any scheme.

This is the sharpest operational limitation of the eFuse-less mode and a
primary motivation for the hardware Secure Boot migration.

## 5. CI pipeline

`.gitea/workflows/firmware-build.yml`:

1. Writes the `OTA_SIGNING_KEY` secret to `/tmp/ota_signing_key.pem` and
   exports `BRAMBLE_OTA_SIGNING_KEY` (fails if unset); the build's
   `ensure-ota-signing-key.sh` copies it to `keys/ota_signing_key.pem`.
2. Builds all boards; `idf.py` signs each `bramble.bin` during the build.
3. **Verifies** each artifact's signature against the committed
   `keys/ota-release-pub.pem` with `espsecure.py verify_signature`; a
   mismatch fails the build. This is an end-to-end build-sign-verify check
   on the real toolchain.
4. Publishes to bramblemesh.org/ota as before. The signature travels inside
   `bramble.bin`, so the artifact index format (`docs/ota-release-schema.md`)
   is unchanged.
5. Removes the key from the runner workspace (`if: always()`).

## 6. Threat coverage and residuals

Prevented: MITM firmware injection, compromised or impersonated update
server, RPC-driven pointing of a device at an attacker URL (origin allowlist
plus signature), corrupted downloads, silent downgrades to vulnerable
versions.

Residual, accepted until the hardware Secure Boot phase:

- **No boot-time enforcement.** The bootloader boots whatever is in flash; a
  physical-access attacker (USB/JTAG) can write unsigned firmware and erase
  the NVS rollback floor. Consistent with SECURITY-MODEL's device-as-secret
  posture: physical possession is already treated as compromise.
- **Signing key compromise** signs valid malicious images until rotated.
- **CI compromise** is equivalent to key compromise (the key lives in CI
  secrets).
- The anti-rollback floor is software state, not an eFuse counter. The
  eFuse-backed hardware floor is designed and host-tested but compile-gated off
  and pending bench validation (`docs/design/ota-antirollback.md`, issue #79).

Hardware Secure Boot V2 plus flash/NVS encryption (ledger SEC-H4) close the
physical-attacker gap; both are human-gated on bench validation with a
sacrificial board and are out of scope here.

## 7. Operator notes

See `docs/ota-rollout.md` for the operator flow (set origin, trigger update
by relative path, deliberate downgrades). RPC surface:

- `bramble.otaUpdate {path, allow_downgrade?}`: path is relative to the
  origin; `url` is rejected.
- `bramble.otaGetOrigin {}`: effective origin, default, override flag,
  rollback floor, running version.
- `bramble.otaSetOrigin {origin}` / `{reset: true}`: validated against the
  same policy as resolution; authenticated like every non-identification RPC.

OTA failures surface in the device log (`ota` / `ota_rollback` tags) and the
most recent failure reason is returned as `last_error` on the next
`bramble.otaUpdate` call.
