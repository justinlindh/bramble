# Mesh-Native Group DMs

**Date:** 2026-02-17
**Status:** Draft
**Author:** Justin (via planning agent)

## Summary

Private group messaging over routed paths — not flooded channels. Members exchange messages that look like ordinary DMs to relay nodes, preserving group membership privacy while avoiding the airtime cost of channel flooding.

This is a novel capability: neither Meshtastic nor MeshCore offers private routed group messaging. Bramble can be the first LoRa mesh protocol to ship it.

---

## 1. Group Creation & Membership

### Group Formation

Groups are created by an **initiator** who selects 1–7 other members (max group size: **8 including initiator**). The 8-member cap is a pragmatic LoRa constraint — a single group message fans out to N-1 unicast DMs, and airtime scales linearly.

**Flow:**

1. Initiator generates a random 16-byte `group_seed`
2. `group_id = BLAKE2s-128(group_seed || sort(member_node_ids...))`
   - Deterministic given the same seed + members
   - 128-bit — collision-resistant, fits in packet headers
3. Initiator sends `GROUP_INVITE` to each prospective member via existing DM routing
4. Members who accept store the group locally and reply with `GROUP_ACK(ACCEPT)`
5. Initiator broadcasts `GROUP_MEMBER_LIST` to all accepted members once quorum is reached (or after timeout)

### Group ID Derivation

```
group_id: [16 bytes] = BLAKE2s(group_seed || sorted_member_ids)
group_seed: [16 bytes] random, generated by initiator
sorted_member_ids: concatenation of all member node_ids (4 bytes each), sorted ascending
```

The `group_seed` prevents attackers who know the member set from predicting the `group_id`.

### Membership Changes

- **Add member:** Initiator sends `GROUP_INVITE` to new member, then `GROUP_MEMBER_UPDATE(ADD)` to existing members. Triggers key rotation (§2).
- **Remove member:** Initiator sends `GROUP_MEMBER_UPDATE(REMOVE)` to remaining members. Triggers key rotation. Removed member is not notified (they simply stop receiving messages).
- **Leave:** Member sends `GROUP_LEAVE` to initiator, who propagates `GROUP_MEMBER_UPDATE(REMOVE)`.
- **Only the initiator can add/remove.** Simplifies consistency. Future work: delegated admin.

### Recommended Group Sizes

| Members | Fan-out DMs per message | Practical? |
|---------|------------------------|------------|
| 2       | 1                      | Just use DMs |
| 3–4     | 2–3                    | Sweet spot |
| 5–6     | 4–5                    | Usable, watch duty cycle |
| 7–8     | 6–7                    | Max recommended |
| >8      | —                      | Reject at creation |

## 2. Key Management

### Approach: Group Epoch Key with Sender Ratchet

We avoid tree-based group DH (too complex for constrained devices, too many round trips over LoRa). Instead:

1. **Group Key (`GK`):** Initiator generates a random 32-byte symmetric key at group creation.
2. **Epoch:** Each membership change increments the epoch counter and derives a new `GK`.
3. **Distribution:** `GK` is encrypted per-member using existing DM session keys and sent inside `GROUP_INVITE` / `GROUP_MEMBER_UPDATE` packets.

```
GK_epoch = HKDF-SHA256(
    ikm = previous_GK || "bramble-group-rekey",
    salt = epoch_counter (4 bytes, big-endian),
    info = group_id,
    len = 32
)
```

For the initial epoch (epoch=0), `GK_0 = group_seed_key` (a separate random 32-byte key generated by the initiator, distinct from `group_seed`).

### Message Encryption

Group messages are **not encrypted with GK directly**. Instead, each sender derives a per-message key:

```
msg_key = HKDF-SHA256(
    ikm = GK_epoch,
    salt = sender_node_id || msg_counter (4 bytes each),
    info = "bramble-group-msg",
    len = 32
)
nonce = first 12 bytes of BLAKE2s(sender_node_id || msg_counter || group_id)
ciphertext = AES-256-GCM(msg_key, nonce, plaintext, aad = group_id || epoch)
```

Each sender maintains their own monotonic `msg_counter` per group per epoch.

### Forward Secrecy

- **Between epochs:** Compromising `GK_epoch` doesn't reveal `GK_epoch-1` (HKDF is one-way).
- **Within an epoch:** Limited. Compromising `GK_epoch` + known counters reveals all messages in that epoch. This is acceptable for group chat — per-message ratcheting would require O(N) state per member.
- **DM layer:** The `GROUP_INVITE` / key distribution messages inherit the forward secrecy of the underlying DM Double-DH sessions.

### Key Rotation Triggers

| Event | Action |
|-------|--------|
| Member added | epoch++, derive new GK, distribute to all |
| Member removed | epoch++, derive new GK, distribute to remaining |
| Manual rotate | Initiator can trigger at any time |
| Epoch counter overflow (2³²) | Rekey with fresh random GK |

## 3. Message Routing

### Approach: Source Fan-Out via Existing DM Routing

**Recommended: fan-out at source.** The sender encrypts the group message N-1 times (once per recipient) and sends N-1 individual DM-routed packets.

**Why not multicast tree?**

| Factor | Fan-out (N DMs) | Multicast tree |
|--------|-----------------|----------------|
| Implementation complexity | Low — reuses DM routing | High — tree construction, maintenance |
| Airtime (best case) | N-1 routed packets | Fewer hops if tree shares paths |
| Airtime (worst case) | Same | Tree maintenance overhead erases savings |
| Privacy | Messages look like unrelated DMs | Tree structure leaks group topology |
| Reliability | Per-path, independent | Single tree failure cascades |
| State required | None beyond existing route cache | Tree state on every relay |

**Verdict:** For groups of 2–8, the airtime difference is small. Fan-out is simpler, more private, and more robust. Multicast trees are a future optimization if groups >8 are ever supported.

### Fan-Out Implementation

```
send_group_message(group, plaintext):
    epoch = group.current_epoch
    sender_counter = group.my_counter++
    msg_key = derive_msg_key(group.GK, my_node_id, sender_counter, epoch)
    ciphertext = aes_gcm_encrypt(msg_key, plaintext, aad = group_id || epoch)

    for member in group.members:
        if member == self: continue
        # Wrap in DM envelope — relay nodes see a normal DM
        dm_payload = GroupMessagePayload {
            group_id,          # 16 bytes (encrypted inside DM layer)
            epoch,             # 4 bytes
            sender_counter,    # 4 bytes
            ciphertext,        # variable
            tag,               # 16 bytes (GCM tag)
        }
        send_dm(dest=member, payload=dm_payload, type=GROUP_MESSAGE)
```

The `GROUP_MESSAGE` type byte is inside the DM encryption envelope — relay nodes see only a standard DM packet with an opaque payload.

### Airtime Budget

Assumptions: 250-byte DM packet, SF10 BW125 (common LoRa config), ~0.5s airtime per packet.

| Group size | Packets per message | Airtime per message |
|------------|--------------------|--------------------|
| 3          | 2                  | ~1.0s              |
| 5          | 4                  | ~2.0s              |
| 8          | 7                  | ~3.5s              |

At 1% duty cycle (36s per hour), an 8-member group can send ~10 messages/hour from one node. Acceptable for LoRa use cases.

## 4. Delivery Tracking

### Per-Member Receipts

Each DM-routed group message already triggers Bramble's standard delivery receipt (`DM_ACK`) from the recipient. The sender collects these per group message:

```
GroupDeliveryState {
    msg_id: [8 bytes]       # BLAKE2s-64(group_id || sender || counter)
    recipients: Map<NodeId, DeliveryStatus>
    # DeliveryStatus: PENDING | DELIVERED | FAILED | EXPIRED
    sent_at: u32            # epoch seconds
    timeout: u16            # seconds before marking EXPIRED (default: 300)
}
```

### Group-Level Confirmation

When all non-self members reach `DELIVERED`:
- Mark message as `ALL_DELIVERED`
- Optionally surface to UI

**No explicit GROUP_ACK is sent back to the group** — that would double airtime. The sender tracks delivery locally from individual DM_ACKs.

### Receipt Privacy

DM_ACKs travel the reverse DM path. Relay nodes see them as ordinary DM receipts — no group information leaks.

## 5. Offline Members

### Graceful Degradation

- Group messages to offline members follow the same path as offline DMs
- If Bramble's store-and-forward (SAF) nodes exist on the route, they buffer as usual
- Sender marks member as `PENDING` → `EXPIRED` after timeout

### Behavior

| Scenario | Handling |
|----------|----------|
| Member temporarily offline | SAF buffers if available; sender retries on next route discovery |
| Member offline > expiry | Sender marks EXPIRED; does NOT remove from group |
| Member offline at invite | Initiator retries GROUP_INVITE periodically (3 attempts, exponential backoff) |
| All retries exhausted | Member stays in group roster but marked UNREACHABLE; messages still attempted |

### Catch-Up

When a previously-offline member comes back online:
- They receive any SAF-buffered messages
- They do NOT request message history from other members (no backfill protocol — too expensive for LoRa)
- If they missed an epoch change, the initiator detects stale epoch in their next message and re-sends the current `GK` via DM

## 6. Protocol Additions

### New Packet Types

All group packet types are **DM-envelope inner types** — they are encrypted inside the DM layer and invisible to relay nodes.

```
DM Inner Type IDs (extending existing enum):
    0x10  GROUP_INVITE
    0x11  GROUP_ACCEPT
    0x12  GROUP_REJECT
    0x13  GROUP_MESSAGE
    0x14  GROUP_MEMBER_UPDATE
    0x15  GROUP_LEAVE
    0x16  GROUP_REKEY
```

### Packet Formats

#### GROUP_INVITE (0x10)

Sent by initiator to each prospective member.

```
┌──────────────────────────────────────────────────────┐
│ DM Envelope (encrypted by DM session key)            │
│ ┌──────────────────────────────────────────────────┐ │
│ │ type:          u8  = 0x10                        │ │
│ │ group_id:      [16 bytes]                        │ │
│ │ group_name:    [0-32 bytes] UTF-8, len-prefixed  │ │
│ │ epoch:         u32 = 0                           │ │
│ │ GK_encrypted:  [32 bytes] (GK, encrypted w/      │ │
│ │                 DM session key — already inside   │ │
│ │                 DM envelope, so this is the raw   │ │
│ │                 GK bytes)                         │ │
│ │ member_count:  u8                                │ │
│ │ members:       [member_count × 4 bytes] node_ids │ │
│ │ group_seed:    [16 bytes]                        │ │
│ └──────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────┘
Max inner payload: 1 + 16 + 33 + 4 + 32 + 1 + 32 + 16 = 135 bytes
```

#### GROUP_ACCEPT / GROUP_REJECT (0x11 / 0x12)

```
┌────────────────────────────────────┐
│ type:      u8  = 0x11 or 0x12     │
│ group_id:  [16 bytes]             │
└────────────────────────────────────┘
Inner payload: 17 bytes
```

#### GROUP_MESSAGE (0x13)

```
┌──────────────────────────────────────────────────────┐
│ type:           u8  = 0x13                           │
│ group_id:       [16 bytes]                           │
│ epoch:          u32                                  │
│ sender_counter: u32                                  │
│ ciphertext:     [variable, up to ~180 bytes]         │
│ gcm_tag:        [16 bytes]                           │
└──────────────────────────────────────────────────────┘
Inner payload: 1 + 16 + 4 + 4 + N + 16 = 41 + N bytes
Max plaintext per message: ~180 bytes (within 250-byte DM packet budget)
```

#### GROUP_MEMBER_UPDATE (0x14)

```
┌──────────────────────────────────────────────────────┐
│ type:         u8  = 0x14                             │
│ group_id:     [16 bytes]                             │
│ action:       u8  (0x01=ADD, 0x02=REMOVE)            │
│ target_node:  [4 bytes] node_id                      │
│ new_epoch:    u32                                    │
│ new_GK:       [32 bytes] (raw, inside DM envelope)   │
│ member_count: u8                                     │
│ members:      [member_count × 4 bytes]               │
└──────────────────────────────────────────────────────┘
```

#### GROUP_LEAVE (0x15)

```
┌────────────────────────────────────┐
│ type:      u8  = 0x15             │
│ group_id:  [16 bytes]             │
└────────────────────────────────────┘
```

#### GROUP_REKEY (0x16)

Same format as GROUP_MEMBER_UPDATE but with `action = 0x00 (REKEY_ONLY)` and no target_node.

### Group Membership Sync

No active sync protocol. The initiator is the source of truth. If a member suspects stale membership (e.g., receives a message from an unknown sender claiming to be in the group), they send a `GROUP_MESSAGE` to the initiator with a sync-request flag (1 byte in message payload). Initiator responds with a full `GROUP_MEMBER_UPDATE`.

## 7. Privacy

### Threat Model

| Observer | What they see | What they learn |
|----------|--------------|-----------------|
| Relay node | Standard DM packets between various pairs | Nothing — group messages are indistinguishable from regular DMs |
| Network-wide passive observer | DM traffic patterns: sender → N destinations in quick succession | Potential correlation if fan-out is simultaneous |
| Compromised group member | All group messages (current epoch) | Group membership, message content |

### Mitigations

1. **Opaque DM payloads:** Group packet types are inside the DM encryption envelope. Relay nodes see `DM_DATA` with an opaque payload.
2. **Fan-out jitter:** Sender staggers the N-1 DMs with random delay (50–500ms between sends). Prevents timing correlation of simultaneous fan-out.
3. **No group metadata in routing headers:** `group_id` never appears in any cleartext header.
4. **Route independence:** Each DM may take a different path. No single relay sees all group traffic.

### Limitation

A persistent passive observer monitoring a sender's RF output can correlate N near-simultaneous DMs to different destinations. Fan-out jitter reduces but doesn't eliminate this. For LoRa mesh, this is an acceptable tradeoff — the alternative (multicast tree) leaks more topology information.

## 8. Integration with Existing Components

### Affected Components

| Component | Changes Required |
|-----------|-----------------|
| `dm_session.rs` | Add inner type dispatch for 0x10–0x16; group message decrypt path |
| `routing.rs` | No changes — group uses existing DM routing |
| `crypto.rs` | Add `derive_group_msg_key()`, `group_rekey()` HKDF functions |
| `packet.rs` | Add group inner packet type enum variants and serialization |
| `delivery.rs` | Extend delivery tracking with per-group, per-member state |
| `store.rs` | Persist group roster, epoch, GK, counters |

### New Component

**`group.rs`** — Group DM manager

Responsibilities:
- Group lifecycle (create, invite, accept, leave, dissolve)
- Group key management (GK storage, epoch tracking, rekey)
- Message fan-out (encrypt + dispatch N-1 DMs)
- Delivery aggregation (collect per-member DM_ACKs → group delivery state)
- Membership state machine

### Storage

```
GroupState (persisted to flash/NVS):
    group_id:       [16 bytes]
    group_name:     String (max 32 bytes)
    group_seed:     [16 bytes]
    role:           INITIATOR | MEMBER
    epoch:          u32
    GK:             [32 bytes]
    members:        Vec<NodeId>  (max 8)
    my_counter:     u32
    peer_counters:  Map<NodeId, u32>  (anti-replay)
    created_at:     u32
```

Estimated per-group storage: ~150 bytes. At 8 groups max: ~1.2 KB.

## 9. Simulator Scenarios

### Scenario 1: Basic Group Creation (3 nodes)

```
Topology: A ←→ B ←→ C  (linear, B relays)

1. A creates group with {A, B, C}
2. A sends GROUP_INVITE to B (direct) and C (via B)
3. B accepts → GROUP_ACK(ACCEPT) to A
4. C accepts → GROUP_ACK(ACCEPT) to A (via B)
5. A sends GROUP_MEMBER_LIST to B and C
6. A sends group message "hello" → DM to B (direct), DM to C (via B)
7. B decrypts, renders. C decrypts, renders.
8. B and C send DM_ACK back to A.
9. A shows "all delivered" ✓
```

**Verify:** B (as relay for A→C) cannot read the group message to C. B receives their own copy as a separate DM.

### Scenario 2: Member Offline & Catch-Up (4 nodes)

```
Topology: A ←→ B ←→ C, A ←→ D

1. Group: {A, B, C, D}. D goes offline.
2. A sends group message → fans out to B, C, D
3. B ack ✓, C ack ✓, D times out → EXPIRED
4. D comes back online, route re-established
5. A sends next group message → D receives it, acks ✓
6. D did NOT receive message from step 2 (no backfill)
```

**Verify:** No crash, no stale state. D's counter picks up correctly.

### Scenario 3: Member Removal & Rekey (5 nodes)

```
Topology: fully connected (all in range)
Group: {A, B, C, D, E}. A is initiator.

1. A removes D from group
2. A increments epoch, derives new GK
3. A sends GROUP_MEMBER_UPDATE(REMOVE, D) to B, C, E with new GK
4. D is not notified
5. A sends group message with new epoch → B, C, E can decrypt
6. D (if still has old GK) cannot decrypt new-epoch messages
```

**Verify:** D cannot decrypt post-removal messages. Epoch mismatch is handled gracefully (D discards, does not crash).

### Scenario 4: Privacy — Relay Cannot Infer Group

```
Topology: A ←→ R ←→ B, A ←→ R ←→ C
R is a relay (not in group). Group: {A, B, C}

1. A sends group message → DM to B via R, DM to C via R
2. R relays both packets
```

**Verify:** R sees two unrelated DM packets (different destinations, different ciphertext). Packet sizes may be similar — fan-out jitter should be applied. R cannot determine A is sending a group message vs. two independent DMs.

### Scenario 5: Airtime Stress Test (8 nodes, max group)

```
Topology: 8 nodes in a 3-hop mesh
Group: all 8 nodes

1. Each node sends one group message in round-robin
2. Measure total airtime per round: 8 senders × 7 DMs = 56 routed packets
3. With multi-hop routing (avg 2 hops): ~112 transmissions
4. At 0.5s each: ~56 seconds of airtime spread across nodes
```

**Verify:** Duty cycle limits are not exceeded on any single node. Message delivery rate > 90% within 60s timeout.

## Open Questions

1. **Should the initiator role be transferable?** Current design: no. If initiator goes permanently offline, group is effectively frozen (no rekeys, no membership changes). Could add `GROUP_TRANSFER_ADMIN` later.
2. **Message deduplication:** If a member receives the same group message via SAF after already receiving it live, the counter-based dedup handles it. But should we keep a sliding window or just last-seen counter?
3. **Group discovery:** Currently groups are invite-only with no advertisement. Is there a use case for "joinable" groups that still use routed (non-flooding) delivery?
4. **Compression:** For fan-out of identical plaintext, could we compress at the DM layer? Probably not worth the complexity for <200 byte payloads.
